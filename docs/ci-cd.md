# CI/CD, tooling, and release strategy

> What runs on every change, how releases happen, and the quality gates around both.
> Workflow files live in `.github/workflows/`.

## 1. Continuous integration (`.github/workflows/ci.yml`)

Runs on every push to `main` and every pull request:

| Step      | Command                                                                           | Gate |
| --------- | --------------------------------------------------------------------------------- | ---- |
| Lint      | `pnpm lint` (ESLint flat config, typescript-eslint recommended + prettier compat) | hard |
| Format    | `pnpm format:check` (Prettier)                                                    | hard |
| Typecheck | `pnpm typecheck` (`tsc --noEmit`, strict)                                         | hard |
| Test      | `pnpm test` (Vitest; coverage enforced once suites exist in M2+)                  | hard |
| Build     | `pnpm build`                                                                      | hard |

Node 24 (active LTS) runtime in CI; engines field requires `>=22` locally (22.x remains in
maintenance LTS until 2027-04).

## 2. Security scanning

| Tool                                     | Workflow                       | What it catches                            |
| ---------------------------------------- | ------------------------------ | ------------------------------------------ |
| GitHub secret scanning + push protection | repo setting (enabled in M1)   | Committed tokens, before they land         |
| gitleaks                                 | `security.yml`                 | Secret patterns in history on PRs/pushes   |
| CodeQL                                   | `codeql.yml` (weekly + on PRs) | JS/TS injection and taint classes          |
| Dependabot                               | `dependabot.yml`               | Stale/vulnerable npm, actions, docker deps |

## 3. Testing strategy

| Layer       | Tooling                                | Scope                                                                       |
| ----------- | -------------------------------------- | --------------------------------------------------------------------------- |
| Unit        | Vitest                                 | Verification engine (pure), crypto module, config parsing, scope derivation |
| Integration | Vitest + real Postgres/Redis (compose) | Services layer, migrations, state store                                     |
| HTTP        | Vitest + supertest                     | OAuth callback state validation and failure paths                           |
| API mocks   | nock / msw                             | GitHub API responses, including rate-limit errors                           |
| E2E         | scripted flow (M6)                     | Full `/link` → callback → role grant with mocked GitHub + Discord           |

Policy: verification engine and crypto require tests with every change; services require
integration coverage for write paths.

## 4. Release pipeline

- **Versioning:** [changesets](https://github.com/changesets/changesets) — `release.yml` maintains
  a version PR on `main`; merging it creates signed git tags (`vX.Y.Z`). No npm publishing — this
  is an application, not a library.
- **Images:** on `v*` tags, `docker.yml` builds a multi-stage distroless-friendly image and pushes
  `ghcr.io/ishannaik/mergeid:<version>` (+ `latest` on the newest release).
- **Changelog:** generated by changesets from conventional-commit PR titles.
- **Environments:** no staging server for v1 — self-hosters pin image tags; the support server runs
  the newest tag.

## 5. Branch protection (recommended on `main`)

- Require pull request before merging; 1 review for security-sensitive paths (`src/crypto`,
  `src/github/oauth.ts`, workflows).
- Require green CI status checks.
- Require linear history (squash merges).
- Restrict force-push and deletion.

## 6. Conventions

- **Commits/PR titles:** Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`,
  `refactor:`, `security:`). Scope optional, e.g. `feat(oauth): validate state single-use`.
- **Formatting:** Prettier is the only formatter; ESLint never formats. Both run in CI.
- **Dependency policy:** add a dependency only when it replaces ≥ ~100 lines of code or a real
  correctness risk; every new dependency must be justified in the PR description.
